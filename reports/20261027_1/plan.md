## 1. 何を作るか

FF14 のフロントライン（3部隊×24人、20分）の試合中に、サブモニタ（Full HD）のブラウザへ表示しておく早見表。重要な仕様と数値を一目で確認できるようにする。ルールごとに1ページ、計5ページ。

| シールロック（争奪戦） | [/frontline/3/](https://jp.finalfantasyxiv.com/lodestone/playguide/contentsguide/frontline/3/) | 情報値 |
| フィールド・オブ・グローリー（砕氷戦） | [/frontline/4/](https://jp.finalfantasyxiv.com/lodestone/playguide/contentsguide/frontline/4/) | 情報値 |

## 3. ゴール・非ゴール・アンチゴール

### ゴール
- G1: 5ルール各1ページ。必要な情報が Full HD の1画面に**スクロールなしで**収まる。
- G2: 各ページに「ルール共通の仕様」と「ルール固有の仕様」を載せる（項目は依頼文のとおり。表現は §2 の読み替えに従う）。
- G3: すべての数値に出典と根拠の等級を付ける。公式以外の値は**ユーザーが採用と判定したものだけ**載せる。
- G4: どのパッチ時点の情報かを明示する。値が変わったら正典データを1か所直すだけで全ページに反映される。
- G5: GitHub Pages（`https://idios.github.io/kobutachan-ffxiv-research/` 配下）で公開する。

### 非ゴール（提案）
- ゲームとの連携（ログ読み取り・オーバーレイ）はしない。FF14 の規約で外部ツールは禁止されている。
- 立ち回りや戦術の解説はしない。仕様と数値に限る。
- スマホ・タブレットへの最適化はしない。
- クリスタルコンフリクト・ライバルウィングズは対象外。

### アンチゴール（動いても失敗とみなすもの・提案）
- スクロールしないと見えない情報がある。
- 試合中の一瞥で読めない（文字が小さい、どこに何があるか探す必要がある）。
- 未確認の値が、公式の値と見分けのつかない形で並ぶ。
- パッチで値が変わったのに、古い値がどこかに残る。

## 4. 前提と制約

- **公開環境（確認済み）**: リポジトリは公開。GitHub Pages は main ブランチ直下を Jekyll でビルドする旧来方式（テーマ cayman）。
  - front matter のない HTML はテーマを通らずにそのまま配信される。既存の予測レポートと干渉しない。
  - ルートに `.nojekyll` は置けない（置くと既存の Markdown レポートが HTML にならなくなる）。
  - 応答に `Cache-Control: max-age=600` が付いているので、更新が閲覧者に届くまで最大10分ほどかかる。
- **権利（スクウェア・エニックス「著作物利用条件」2026-10-14 改訂版）**:
  - 非商用であれば、公式サイトの文章・情報・画像とゲーム内のスクリーンショットを使ってよい。
  - 各ページに「© SQUARE ENIX」を1行入れる。
  - 広告・寄付・スポンサーのリンクは置けない（寄付の募集も商用扱い）。
  - 利用は「日本国内に限定」とされている。
  - 過度な加工・改変は禁止。
  - データ解析で抽出した素材（マップ画像など）は使わない。
- **他のファン資料**: consolegameswiki の本文は GFDL、Lodestone 日記は各著者の著作物。数値（事実）を出典つきで引用するだけにし、文章や表をそのまま写さない。
- **リポジトリ規約（AGENTS.md）**: 派生値を手で書かない／尺度規約を宣言する／訂正・撤回を全文書へ伝播させる／根拠の等級を付ける／検証の途中経過を収束と言わない。
- **ゲームのバージョン**: 現行は 7.57（2026-10-13）。8.0 は 2027年1月の予定と報じられていて、PvP の更新も含むと告知されている。8.0 で多くの値が変わる前提で作る。
- **ローカル環境（確認済み）**: Python 3.12（tomllib・PyYAML・Playwright あり）、Edge・Chrome あり。

### 5.3 設計に効く発見

1. **時刻表より「時間帯の帯」と「規則」。**
   - 時刻（または時間の幅）で書けるのは次のものだけ。
     - 各ルールの初回の出現（ただし出典が1件だけのものが多い）
     - 砕氷戦の小の一斉出現
     - 同時上限の切り替わり
     - 演習戦の天候の窓（幅で）
   - それ以外は「消えてから○秒後に次が出る」といった規則で書くことになる。タイムラインは「残り時間の帯（20:00→0:00）に上限数・天候の窓・固定イベントを重ねた図」と「規則の短文」で表すのが現実的。
2. **「時間あたり」の計算にはランク出現率が要るが、どのルールでも見つかっていない。** 確率の要る期待値（例: リス1基あたりの平均）は数値で出せない。1個あたりの値と速度は出せる。
3. **「今日のルール」を自動表示できる。** 7.5 から8日周期が公式。起点については次のとおり。
   - 外部の3系統のうち2系統（pvp-calendar のコード、tuyurukai のカレンダーのコード）は「2026-04-29＝外縁遺跡群」で一致する。ここから数えると 2026-10-27 はオンサル・ハカイル。
   - wiki の式だけが1日ずれていて、演習戦になる。
   - [Observed] ゲーム内で1日確認すれば確定する。
4. **8.0（2027年1月予定と報道）で大きく変わる可能性が高い。** 版の表示と更新手順を最初から組み込む。ファンフェス東京の基調講演（2026-10-31 予定と検索結果にある）で、8.0 の PvP の変更が発表される可能性もある。
5. **点の配り方が4通りある。** 値ごとに配り方を明記しないと読み違える。
   - 部隊全体: 外縁遺跡群の拠点。占拠の総数で決まり、拠点1つずつの値ではない
   - 与ダメージの割合: ドローン・システム・氷
   - 受けた部隊の数で等分: 邀撃コマンダー
   - 占拠した部隊だけ: リス・無垢の土地・戦略目標地
6. **鮮度は項目ごとに「最後に公式で変わったパッチ」で判定する。** 「6.1 より前は一律に無効」とは切れない。シールロックのリスの値は 3.05 から、オンサルの撃破±は 5.18 から変わっていない。逆にジョブ補正と戦意値は 7.55 で変わった。HotFix（例: 2025-12-25 の帰還0秒、シールロックのリスがすぐ再起動した不具合の修正）も対象に入れる。
7. **LB ゲージの仕組みに未確定な点がある。** ゲージが戦闘中だけ増えるのか、生きている間はずっと増えるのか。順位の倍率がヴァイパーの加算やオーロラにも掛かるのか。順位補正込みの秒数や、オーロラ中の秒数は、この前提つきの計算値になる。
8. **実測は外部ツールなしでできる。** 自分の録画と、ゲーム内の表示（スコアHUD、演習戦のバトルログ、チャットのタイムスタンプ）を使う。FF14 の規約で外部ツール（ACT、Dalamud など）は使えない。

## 7. 技術方針（提案）

- 静的な HTML と CSS。JavaScript は必要な機能（今日のルールの表示、画面への拡大縮小、自分のジョブの強調、任意のタイマー）だけに使う。フレームワークは使わない。
- トップページ（`…/frontline/`）は5ルール分を内包し、開いた日のルールを表示する。切替は毎日 0:00 JST（15:00 UTC）で、閲覧者の時間帯によらず判定する。リダイレクトしないので、日付をまたいだあとにリロードすると表示が切り替わる。ほかのルールへはタブで移れる。
- 根拠の等級はアイコンで示す（外部・実測・計算・未確認）。公式の値は無印。アイコンにはマウスを乗せると説明が出るようにし、凡例をフッタに置く。
- 図やアイコンは公式サイトの素材（ファンキット、ガイドの画像、ジョブガイドのアイコン）を使う。足りないものは自作の図形（ランクの △◇⬠ など）。
- 正典データは**値台帳（Markdown の表）**。ユーザーが ○×とコメントを直接書き込め、GitHub 上でもそのまま読める。`frontline/tools/ledger.py` が列・ID・等級・出典の参照・原文抜粋の有無を検査する（R4・A4）。
- Python の生成スクリプトが値台帳から HTML を作る。生成物もコミットするので、GitHub Pages の設定は変えずに済む。
- 派生値（1分あたり、絶対秒、合計点など）は生成スクリプトで計算する。テンプレートに数値を手で書かない。
- 自動検査（pytest）:
  1. 派生値の計算
  2. 画面に出る数値がすべて正典データに辿れること
  3. 撤回した値・旧パッチの値がどこにも残っていないこと（不在検査。旧値は「なぜ使わないか」とセットで登録簿に残す）
  4. Playwright で、想定する表示領域すべて（A2 の回答で決める。例: 1920×1080、最大化ウィンドウ相当、1536×864）について、スクロールが出ないことと、文字が下限より小さくならないこと（「一瞥で読める」アンチゴールの検査）
  5. 検査器そのものの変異テスト。旧値を全ページへ注入したら検出されること。検出できない検査器は証拠にしない（analysis-integrity スキルの手順）
  - 不在検査の対象は、公開ページと正典データ。調査メモは旧値を意図的に含むので対象外にする。
- 公開 URL: `…/kobutachan-ffxiv-research/frontline/`（トップ＝今日のルール）と `…/frontline/<ルール>/`。値台帳と出典は `frontline/data/`、計画と調査メモは `reports/20261027_1/`。
- 画面: 固定キャンバスで設計し、表示領域に合わせて全体を拡大縮小する。キャンバスの縦横比は、実際の表示領域（§11 A2）に合わせる。16:9 で作ってウィンドウに縮めると、全体が1割ほど小さくなるため。ゲーム画面の横で眩しくない暗い配色にする。

## 8. データ設計（提案）

- 値台帳は1行に1つの値: ID／区分／項目／値／単位／条件・配り方（§5.3 の4通り）／等級／出典（ID）／最終変更（公式で最後に変わったパッチ）／現行確認／採否（○×）／コメント。公式の原文抜粋と備考は、同じファイルの「根拠」の表に置く。
- 出典は `frontline/data/sources.md`（ID／種別／名称／URL／公開・更新／対象パッチ／取得日／系統／保存方針／既存アーカイブ）。公式の抜粋は `frontline/data/official/`。ゲーム内確認は `frontline/data/ingame-checks.md`。
- 根拠の等級は、AGENTS.md の等級をゲーム仕様に当てはめる（案）。事前調査では調査役ごとに証拠の種類の付け方がばらついたので、P1 でこの表に統一する:

  | 等級 | 意味 | 画面上の印（案） |
  |---|---|---|
  | `[Company]` | 公式ガイド・パッチノート・ジョブガイド・HotFix 告知の値 | 公式 |
  | `[Observed]` | ユーザーがゲーム内で確認した値 | 実測 |
  | `[Observed]` | 測り方の書かれた外部の実測、独立した2系統以上で一致した外部値 | 外部 |
  | `[Estimate]` | 確定した値からの計算（1分あたり、基準＋補正の実秒など）。前提を値のそばに書く | 計算 |
  | `[Hypothesis]` | 単一の弱い出典・伝聞・測り方不明。前提が未確定の計算（順位補正込みの LB 秒など）。データ解析で見つけただけでゲーム内では未確認のもの | 未確認 |

  あなたが確かめた値と、外部資料が一致しただけの値は、同じ `[Observed]` でも画面の印を分ける（作り手チェックの指摘による。Claude の判断）。

- 鮮度の判定: 項目ごとに「最後に公式で変わったパッチ（HotFix を含む）」を持たせる。それより前の外部情報は自動で「古い可能性」とする。一律の線引きはしない。
- 尺度規約（全ページ共通・案）:
  - 時刻は試合内の**残り時間**（20:00 → 0:00）
  - 時間あたりは**1分あたり**を主にし、**3秒ごと**（ゲームの加算単位）を添える（§11 A7 で確定）
  - 値の名前はルールごとの公式名称
  - パッチ番号と確認日を載せる
  - 期待値の前提（取り分・分母）を値のそばに書く

## 12. Claude が決めたこと（読むときに確かめてほしい判断）

作り手チェックで見つかった文書内の矛盾は、次のように直した。違和感があれば指摘してほしい。

1. **計算値と、その前提の注記は1組で扱う。** 前提を書く場所がなければ、計算値ごと載せない。画面からあふれたときに削る順は、要望外の追加情報 → 計算値（前提とセット）→ 注記。依頼項目そのものは削らない。それでも収まらなければ共通欄を詰める（ジョブ表の行間など）。それでも無理なら相談する。
2. **画面の印を5種類にした。** 公式／実測（あなたがゲーム内で確認）／外部（独立した複数の出典が一致）／計算／未確認。外部資料が一致しただけの値に「実測」の印は付けない。
3. **順位補正込みの LB 秒は、LB ゲージの仕組みが確定するまで載せない。** 載せるとしても未確認の印にする。基準＋補正の実秒（公式値の足し算）は載せる。
4. **キャンバスの縦横比は、実際の表示領域に合わせる。** 自動検査は、想定するすべての表示領域で「スクロールなし」と「文字の下限」を確かめる。
5. **G3（あなたが判定したものだけ載せる）を優先する。** A4 の既定を「黙っていたら採用しない」に改め、一括承認で手間を減らす形にした。
6. **不在検査（旧値が残っていないか）の対象は、公開ページと正典データだけ。** 調査メモは旧値を意図的に含むので対象外にする。
7. **試作図の値は「○○」の伏せ字にした。** 未判定の値の見せ方（A4）が決まるまで、候補値を例として描かない。
